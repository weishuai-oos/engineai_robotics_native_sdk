EngineAI Native SDK 真机部署流程
================================

适用仓库：engineai_robotics_native_sdk
适用分支：当前分支 feature/motion_transition
目标设备：NVIDIA Jetson AGX Orin 64GB（aarch64/ARM64）

本文只针对 T800 机器人，包含“sim to sim”和“sim to real”的代码检查结论、交叉编译、下发、真机启动和调试电脑监测流程。
文中的产品名固定使用 t800，不适用于其他机型。

================================================================
一、先说结论：sim 和 real 是否一致
================================================================

结论：不是完全一致，但主体控制链路是共用的，差异主要集中在运行环境和硬件 I/O；因此不能把 sim 通过简单改名当成 real。

1. 共用部分

- task_motion/default.yaml 及其动作状态机由 sim、robot 共用。
- T800 的绝大多数 runner、动作配置、策略配置和产品资源由同一套源码/配置生成。
- sim 中 MuJoCo 用 TorqueController 将期望关节位置、速度、前馈力矩转换为仿真力矩；real 中则经 imu、motor、硬件接口和真实电机执行。
- install.sh 会把当前构建产物、T800 配置和机器人资源作为同一版本下发，release_note.txt 会记录下发版本。

2. 已确认的差异

- mode.yaml 的 active_mode 不同：本地仿真使用 sim，真机下发后使用 robot。
- task_resident/sim.yaml 使用 sim_subscribe、sim_publish；task_resident/robot.yaml 使用 imu、motor。真机还会启用 joint_motor_transform_runner 和 motor_runner。
- robot 的 LCM 配置开启 multicast，sim 的 LCM 配置关闭 multicast。真机通过局域网接收虚拟手柄时依赖这个差异。
- pd_stand 的真机配置增加 initial_joint_position_bias_threshold: 1.2；MuJoCo 中会跳过真实电机的关节偏置安全检查。
- t800 的 pd_stand 目标站立姿态存在真实机与仿真的膝关节参数差异。
- T800 的 sim 和 robot 输入仲裁周期均为 0.002 秒；T800 的 robot pd_stand 配置增加 initial_joint_position_bias_threshold: 1.2，且站立目标中的膝关节参数与 sim 配置不同。

3. 工程判断

可以认为“动作状态机和大部分控制逻辑保持一致”，不能认为“sim 与 real 的运行时、时序、硬件数据源和安全约束完全一致”。
真机验证必须使用 robot mode、aarch64 构建产物和实际硬件，不能只在 MuJoCo 中验证通过就直接上地面运行。

================================================================
二、部署角色和变量
================================================================

调试电脑（PC）负责：

- 保存完整 Git 仓库。
- 在 Docker/ROS2 环境中做 x86_64 仿真和 ROS2 工具调试。
- 交叉编译 aarch64 真机产物。
- 通过 install.sh 将真机运行包 rsync 到 Jetson。
- 可选：运行 PlotJuggler、虚拟手柄和 ROS2 监测命令。

Jetson 负责：

- 保存 install.sh 下发的真机运行包。
- 使用 Jetson 上预装的 ROS2、运控/电机服务和硬件资源。
- 启动 _install/bin/src_executor，执行真实机器人控制。

本文流程固定使用以下 T800 部署参数：

    MODEL=t800
    ROBOT_USER=user
    ROBOT_HOST=192.168.0.163

================================================================
三、Jetson 上需要有什么代码和环境
================================================================

通过 install.sh 下发时，不需要在 Jetson 上重新 clone 完整源码，也不需要把 PC 的 x86_64 build 目录复制过去。
Jetson 上最终需要类似下面的专用目录：

    ~/projects/engineai_robotics/
    ├── _install/
    │   ├── bin/src_executor
    │   ├── lib/...
    │   └── engineai_robotics_third_party/...
    ├── assets/config/t800/...
    ├── assets/resource/robot/t800/...         （仓库存在时）
    ├── assets/resource/t800.xml               （仓库存在时）
    ├── run_robot.sh
    ├── set_imu_tty.sh
    └── release_note.txt

其中：

- _install/bin/src_executor 必须是 aarch64/ARM64 可执行文件。
- assets/config/t800 是 T800 配置，install.sh 会把 active_mode 自动改为 robot。
- run_robot.sh 和 set_imu_tty.sh 是真机启动脚本。
- /opt/ros/<distro>、/opt/engineai_robotics_hardware、/dev/ttyACM0 等不由 install.sh 下发，它们必须预先存在于 Jetson 系统中。
- 不要在 Jetson 上运行 run.sh；run.sh 是当前仓库的 x86_64 仿真入口，会寻找 build/x86_64/_install 和 MuJoCo 环境。

Jetson 首次部署前应确认：

    uname -m                         # 应输出 aarch64
    ls /opt/ros                      # 至少有 humble 或 jazzy
    test -d /opt/engineai_robotics_hardware
    test -e /dev/ttyACM0

run_robot.sh 会优先选择 /opt/ros/humble；如果 humble 和 jazzy 同时存在，它会优先使用 humble。
因此构建、下发和 Jetson 实际选用的 ROS2 发行版必须保持一致。本文主流程使用 humble。

================================================================
四、调试电脑首次准备
================================================================

1. 进入当前仓库

    cd <调试电脑上的>/engineai_robotics_native_sdk
    git status
    git branch --show-current

确认使用的是要部署的提交；不要在 build 或 install 中混用其他分支的产物。

2. 验证局域网和 SSH

    ping 192.168.0.163
    ssh user@192.168.0.163 'uname -m; ls /opt/ros; test -d /opt/engineai_robotics_hardware'

install.sh 使用 rsync 和 SSH 控制连接，调试电脑和 Jetson 两端都需要可用的 ssh/rsync。
如登录用户名、IP 或目录不同，先编辑仓库根目录的 install.sh：

    remote_user="user"
    remote_host="192.168.0.163"
    remote_dir="~/projects/engineai_robotics"

3. 生成调试容器（PC 已配置过可跳过）

在调试电脑仓库根目录执行：

    ./docker/generate.sh
    engineai_robotics_env

后续仿真和 ROS2 工具命令均应在这个容器内执行；交叉编译命令从容器退出后，在调试电脑宿主机执行。



================================================================
六、在调试电脑交叉编译 Jetson 真机包
================================================================

1. 确认已经退出 engineai_robotics_env 容器，回到调试电脑宿主机。

2. 默认 Jetson AGX Orin 64GB 使用 aarch64，并按 Jetson 上实际 ROS2 版本编译。Humble 示例：

    cd <仓库目录>
    ./build.sh -a aarch64 -r humble -t release

如果 Jetson 只有 jazzy，则使用：

    ./build.sh -a aarch64 -r jazzy -t release

但当前 run_robot.sh 会在 humble 存在时优先选择 humble；不要在 Jetson 同时安装两个发行版后又用不同版本构建。

交叉编译依赖 Docker，并使用仓库已有的 cross_compile_env.sh 和对应 ARM64/ROS 镜像；不需要在 Jetson 上编译。

3. 编译成功后，真机安装目录应为：

    build/aarch64/_install

至少检查可执行文件架构：

    file build/aarch64/_install/bin/src_executor

输出应包含 ARM aarch64/ARM64，而不是 x86-64。

注意：build.sh 会另外生成 build/aarch64/ros2_env/install。这个目录用于对应构建环境的 ROS2 消息/工具，不要把 x86_64 的 _install 下发到 Jetson。

================================================================
七、从调试电脑下发真机包
================================================================

在调试电脑仓库根目录执行：

    ./install.sh t800 robot aarch64

必须显式填写 aarch64。install.sh 默认是 x86_64，省略架构会把错误架构的产物作为默认目标。

install.sh 会完成以下事情：

- 读取 build/aarch64/_install。
- 复制 run_robot.sh、set_imu_tty.sh。
- 复制 T800 的 assets/config 和机器人资源。
- 生成 release_note.txt。
- 通过 rsync 下发到 ~/projects/engineai_robotics。
- 只在远端目录内把 T800 的 active_mode 改成 robot。

重要安全事项：install.sh 对远端部署目录使用 rsync --delete。remote_dir 必须是专用的 Native SDK 部署目录；不要把它设置为 Jetson 的 home 目录或包含其他重要文件的目录。

下发后，在调试电脑检查 Jetson：

    ssh user@192.168.0.163
    uname -m
    cd ~/projects/engineai_robotics
    grep -n '^active_mode:' assets/config/t800/mode.yaml
    test -x _install/bin/src_executor
    cat release_note.txt

active_mode 应为 robot，src_executor 应存在且可执行。

================================================================
八、Jetson 真机运行
================================================================

真机运行前必须完成以下安全准备：

- 确认机器人没有同时运行 robotics.service 和 Native SDK 的 src_executor。

1. SSH 登录 Jetson 并停止自启动运控程序

    ssh user@192.168.0.163
    sudo systemctl stop robotics.service
    cd ~/projects/engineai_robotics

run_robot.sh 使用当前工作目录作为 ENGINEAI_ROBOTICS_DIR，所以 cd 到部署根目录是必须的。

2. 再检查目标配置和设备

    grep -n '^active_mode:' assets/config/t800/mode.yaml
    test -x _install/bin/src_executor
    test -e /dev/ttyACM0
    ls -l /dev/input/js0 2>/dev/null || true
    ls -l /dev/ttyJS 2>/dev/null || true

当前仓库的硬件输入实现可能使用 F710/F310 对应的 /dev/input/js0，RC02 可能使用 /dev/ttyJS；/dev/ttyACM0 还用于真机硬件权限设置。设备节点名称必须以 Jetson 实际系统为准。

3. 前台启动（首次运行推荐）

    sudo ./run_robot.sh t800

例如：

    sudo ./run_robot.sh t800

前台运行可以直接看到日志，便于确认 IMU、电机、ROS2 bridge 和动作状态。先用遥控器保持 passive/安全状态，逐步切换到 PD Stand，再根据产品操作说明进入其他动作。

4. 后台启动

确认前台运行已经验证通过后，才使用后台方式：

    sudo -v
    nohup sudo ./run_robot.sh t800 > nohup.out 2>&1 &
    tail -f nohup.out

另开 SSH 窗口观察进程：

    pgrep -af src_executor

停止后台进程时，先使用 pgrep 输出确认 PID 确实属于本次 Native SDK，再结束该 PID；确认 src_executor 已退出后，才按需要恢复系统服务：

    sudo systemctl start robotics.service

不要在 src_executor 仍运行时启动 robotics.service，避免两个运控程序同时访问电机。

================================================================
九、调试电脑上的 ROS2 数据监测和 PlotJuggler
================================================================

真机启动后，Native SDK 的 ros2_bridge 会从 Jetson 发布 ROS2 数据。调试电脑不需要再运行一份 src_executor，只需要在同一局域网、同一 ROS_DOMAIN_ID 下订阅。

当前仓库的 build.sh 实际生成路径是：

    build/x86_64/ros2_env/install

而 scripts/run_plotjuggler.sh 和旧说明仍然寻找 build/ros2_env/install。这个路径目前不一致，因此直接执行官方示例的 ./scripts/run_plotjuggler.sh remote 可能报“ROS 环境不存在”。本流程使用实际生成路径直接启动。

在调试电脑进入容器，在仓库根目录执行：

    engineai_robotics_env
    cd <仓库目录>
    ./build.sh -r humble -t release
    source build/x86_64/ros2_env/install/setup.bash
    export ROS_DOMAIN_ID=69
    export ROS_LOCALHOST_ONLY=0
    ros2 topic list
    ros2 topic hz /hardware/joint_state
    ros2 topic echo /hardware/imu_info --once
    ros2 run plotjuggler plotjuggler -n

在 PlotJuggler 中选择 ROS2 数据源，并加载：

    scripts/plotjuggler/common_data_display.xml

当前 ros2_bridge 默认对外发布的主要数据包括：

    /hardware/imu_info
    /hardware/gamepad_keys
    /hardware/motor_debug
    /hardware/power_info
    /hardware/motor_state
    /hardware/motor_command
    /hardware/joint_state
    /hardware/joint_command_feedback

这些状态/反馈主题的消息源在 Jetson 真机侧；调试电脑主要订阅和可视化，不要把 PlotJuggler 当作电机控制入口。

================================================================
十、可选：调试电脑运行虚拟手柄
================================================================

只有在确认机器人处于安全状态、人员已远离且物理急停可随时使用时，才启用虚拟手柄。

在调试电脑仓库根目录执行：

    cd tools/virtual_gamepad
    python3 -m venv .venv
    . .venv/bin/activate
    pip install -r requirements.txt
    python3 virtual_gamepad.py

真机 robot LCM 配置使用 multicast，默认地址与虚拟手柄的 239.255.76.67:7667 一致；如果界面能启动但 Jetson 收不到消息，检查交换机/AP 是否允许组播、电脑防火墙和机器人网卡是否在同一局域网。

虚拟手柄只是调试输入，不能代替急停遥控器，也不能代替真实机器人上的安全状态切换。

================================================================
十一、常见问题排查
================================================================

1. Jetson 启动时报架构错误

- 检查 file build/aarch64/_install/bin/src_executor。
- 确认 install.sh 最后一个参数是 aarch64。
- 不要把 build/x86_64/_install 下发到 Jetson。

2. 找不到 ROS2

- Jetson 检查 ls /opt/ros。
- run_robot.sh 当前会优先选择 humble；构建版本要与此一致。
- 调试电脑的 ROS_DOMAIN_ID 必须设为 69，ROS_LOCALHOST_ONLY 必须设为 0。

3. 找不到串口或硬件

- 检查 /dev/ttyACM0、/dev/input/js0、/dev/ttyJS 的实际设备名和权限。
- 确认 /opt/engineai_robotics_hardware 已由机器人系统预装。
- 检查 robotics.service 已停止，并且没有其他 src_executor/motor_service_server 占用资源。

4. 下发后仍然运行 sim

- 在 Jetson 部署目录执行 grep active_mode assets/config/t800/mode.yaml。
- 必须显示 active_mode: robot。
- 确认实际启动的是 sudo ./run_robot.sh t800，不是 ./run.sh。

5. PlotJuggler 启动失败

- 先确认 source build/x86_64/ros2_env/install/setup.bash 已成功。
- 确认 ros2 topic list 能看到 ROS2 环境。
- 当前 scripts/run_plotjuggler.sh 仍使用 build/ros2_env/install 旧路径；需要修脚本后才能直接使用该封装脚本。

6. ROS2 能启动但看不到真机 topic

- Jetson 的 robot mode 必须包含 ros2_bridge。
- 两端使用相同 ROS_DOMAIN_ID=69。
- 两端不能设置 ROS_LOCALHOST_ONLY=1。
- 检查局域网、防火墙、DDS 网卡选择和容器的 host 网络配置。

================================================================
十二、每次真机部署的最小检查清单
================================================================

[ ] 确认当前 Git 分支/提交，且配置和命令均为 T800。
[ ] 仿真使用 active_mode: sim，并完成基础动作验证。
[ ] 使用 ./build.sh -a aarch64 -r <实际 ROS 版本> -t release。
[ ] file 检查 src_executor 为 ARM64/aarch64。
[ ] 使用 ./install.sh t800 robot aarch64 下发，未省略架构参数。
[ ] Jetson 上 active_mode 为 robot，release_note.txt 与本次构建一致。
[ ] Jetson 上 robotics.service 已停止，且没有第二个运控进程。
[ ] 急停遥控器可用，人员已离开危险范围。
[ ] 首次先吊架验证 PD Stand、姿态、关节方向和电机响应。
[ ] 调试电脑 ROS2 使用 DOMAIN_ID=69、ROS_LOCALHOST_ONLY=0。
[ ] 真机停止后，再决定是否恢复 robotics.service。

================================================================
十三、当前仓库需要注意的实现问题
================================================================

- build.sh 生成 build/<arch>/ros2_env/install，但 run_plotjuggler.sh 寻找 build/ros2_env/install；本流程已给出绕过方式，建议后续统一脚本和文档路径。
- T800 的 sim/robot pd_stand 目标姿态和 robot 安全阈值存在差异；首次真机运行必须按本文的吊架、PD Stand 和急停流程验证。
- tools/virtual_gamepad/README.md 中示例文件名与当前实际入口 virtual_gamepad.py 不一致；本流程使用实际存在的入口文件。
- 以上问题不改变“真机必须使用 robot mode + aarch64 包 + 实际硬件”的部署原则。
